# 探索、开发、审核

把发现与交付视为同一个反馈系统：通过完整的垂直切片推进产品，同时主动尝试证伪当前设计，只有可观察的完成门槛全部通过后才结束。本技能是**编排层**——同时应用任务触发的更窄技能（诊断、领域建模、原型、测试驱动开发、前端设计、部署），始终以仓库指令和用户授权为准。

## 适用判断

| 场景 | 是否用本技能 |
|---|---|
| 高不确定性，需实现中持续探索 | ✅ |
| 跨边界/跨模块，需协调多子代理 | ✅ |
| 需将原型推进到生产、反复运行期验证 | ✅ |
| 规格明确的功能开发 | ❌ 直接实现 |
| 琐碎修改或单行修复 | ❌ 直接改 |
| 纯诊断/调试请求 | ❌ 用 `diagnosing-bugs` |
| 纯状态或报告请求 | ❌ 直接做 |

## 严守授权边界

- 区分只读分析、本地实现、外部状态变更和破坏性操作。
- 仅在请求授权修改时实施。纯设计请求只运行探索与审核，不悄然进入实现；混合请求不得把诊断、审核或报告内容视为修改授权。
- 自主执行、持续推进或使用大量子代理的要求，不得扩大原请求涉及的系统、数据、人员或外部操作范围。
- 仅当缺失决策会实质性改变结果且无法从源代码证据中确定时提问；否则说明假设并继续推进。

## 调整执行深度

选择能够现实地证伪方案的最小深度，根据证据动态升降：

| 深度 | 适用 | 做法 | 控制状态 |
|---|---|---|---|
| 精简 | 边界明确但非琐碎的改动 | 一个聚焦周期，直接证据已充分时不派子代理 | 仅工作记忆 |
| 标准 | 跨模块或面向用户的工作 | 一个或多个自适应切片 + 运行期验证 + 独立审核 | 轻量模板 |
| 深入 | 高歧义/高风险/架构性 | 并行探索、备选方案、原型、多审核视角、反复验证 | 轻量模板 |

不得为填满代理名额或完成仪式而增加审核轮次。

## 维护控制状态

开始修改前，先建立与执行深度相称的控制状态。对于标准/深入任务、并行工作或已需重排计划的任务，使用 [references/control-state.md](references/control-state.md) 中的轻量模板。精简任务只在记忆中记录结果、授权边界、完成门槛和下一个决定性检查。

无论采用哪种深度，都要在出现重大新发现、预测失败、范围变化或门槛完成后更新状态。上下文压缩后从该状态继续，不得重新开始。对于标准/深入任务，只保留一个顶层计划步骤处于进行中，并行子代理工作记录在该步骤内。

## 运行自适应循环

```text
框定 → 基线 → 探索 → 规划切片 → 边开发边探索 → 对抗审核 → 决定
 ↑                                                │            │
 └──────────────── 迭代（证据可回退重排）──────────┘            │
                                                               ├─ 完成
                                                               └─ 升级处理
```

满足门控则推进，不满足则继续当前阶段；证据推翻前阶段则回退重排。门控防虚假进展，不防合理回退。

### 1. 框定结果

把请求转换为可观察行为，而不是实现清单。定义工作完成后用户/调用方/运维者/审核者能观察到什么；定义必须保持的不变量；定义明确的非目标，防止相邻发现扩大范围；为每个完成门槛确定成本最低且决定性的证据。对扩展、复刻、迁移或标准对齐工作，先验证底层产品原则或领域原则。优先采用"用户能沿每条受支持路径完成流程"这类结果条件，而非"增加三个特判"。

**完成门控：**
- [ ] 可观察结果已定义（非实现清单）
- [ ] 非目标已明确
- [ ] 完成门槛与决定性证据已定义

**推进/回退：** 满足→推进至基线；后续发现结果定义错误→回本阶段重框。

### 2. 建立基线

选择方案前，建立由代码和真实运行行为支撑的模型。阅读适用的仓库指令、`CONTEXT.md`、局部架构决策和任务专用技能；编辑前检查工作树，保留用户改动并识别重叠文件；追踪相关入口、数据流、状态所有权、生命周期、错误路径、测试、日志和界面；尽可能复现或测量当前行为，建立最紧密的相关反馈信号；行为依赖集成、布局、时序、渲染或环境时检查真实界面；从项目脚本或工具帮助确定命令，不得假设熟悉工具支持熟悉选项。只要实现或运行环境能直接回答，就不得把文档、测试名或早先代理摘要当作证明。

**完成门控：**
- [ ] 相关代码路径、数据流、状态归属已追踪
- [ ] 当前行为已观察或复现（建立最紧密反馈信号）
- [ ] 工作树已检查（用户改动与重叠文件已识别）

**推进/回退：** 满足→推进至探索；基线事实推翻框定→回阶段 1。

### 3. 探索方案空间

只探索会实质性影响结果或模块职责的决策。确实存在重大决策时，形成 2–4 个可信假设或设计；比较结果覆盖、与已验证事实的契合度、职责归属、接口深度、可维护性、可测试性、可逆性、迁移成本和失败模式；用证据淘汰方案，不得按直觉或代理投票决定；选择工作假设，并说明什么观察会证伪它。当源代码事实只留下唯一正确路径时，不要人为制造备选方案。只有当一次性原型是回答设计问题的最低成本方式时才构建原型，并将原型代码与生产改动隔离。

**完成门控：**
- [ ] 工作假设已选定并声明证伪条件（或源码事实只剩唯一路径）

**推进/回退：** 满足→推进至规划切片；假设被证伪→回本阶段换假设。

### 4. 规划垂直切片

把工作假设转化为自适应切片，让每个切片同时产出可用能力和新信息。记录每个切片：面向用户或系统级的结果、它解决的不确定性、所属文件或职责边界、聚焦验证和真实运行面检查、必须触发重排计划的观察结果。按不确定性、风险和杠杆效应综合排序，优先选择最小但完整的端到端路径，不要先堆叠彼此断开的基础设施或薄委托层。后续切片保持可调整。

**完成门控：**
- [ ] 首切片为最小完整端到端路径
- [ ] 切片简报已记录（结果/范围/验证/证伪条件，见 [references/control-state.md](references/control-state.md)）

**推进/回退：** 满足→推进至开发；切片揭示框定错误→回阶段 1。

### 5. 边开发边探索

在每个切片内重复短反馈循环：预测 → 实现或原型 → 观察 → 对比 → 更新模型 → 验证。编辑前先读取狭窄的相关源码，把行为放到真正拥有该职责的模块中；只做能运行端到端行为的最小完整改动；每次有意义的修改后先运行最快的聚焦检查，再按风险扩大验证范围；尽早操作真实运行环境。观察能力不足时可加临时仪表，完成前移除本任务引入的仪表，或按项目日志规范正式纳入。把每个重大新发现固化为测试、不变量、决策、文档更新或明确剩余风险；修复根因和生命周期契约，而非只修某个场景的症状；行为或项目规则变化时按最小原则同步文档。

出现意外结果时，暂停相关编辑并分类处置：

| 意外结果类型 | 处置 |
|---|---|
| 推翻当前模型 | 回基线或探索，重排计划 |
| 阻断完成门槛 | 加入当前或下一个切片 |
| 范围内且高杠杆 | 用证据和验证解决 |
| 相邻但不阻断 | 记录到延后清单后继续 |
| 无关 | 保持不动，有实质价值时才报告 |

**完成门控：**
- [ ] 切片端到端可运行
- [ ] 聚焦检查通过
- [ ] 重大新发现已固化（测试/不变量/决策/文档/明确风险）

**推进/回退：** 满足→进入对抗审核；意外结果按上表处置。

### 6. 对抗性审核

以证伪结果为目的审核，而不是确认投入。按需选择 [references/review-lenses.md](references/review-lenses.md) 中的审核视角——只选与任务相关的，用它们找反例，不生成冗长清单报告。把每个完成门槛追溯到直接证据；审查完整变更差异和周边契约，查找职责泄漏、概念重复、隐藏生命周期假设、失效分支和与用户改动的意外重叠；按项目能力运行聚焦测试、相关更广测试、类型/静态检查、构建和规范检查；验证真实用户或运维界面，包括失败、恢复、销毁、重复使用和边界状态；对照基线检查最终工作树和相关文件清单，包括文档、生成产物、迁移、被忽略/未跟踪缓存、日志和临时文件。只能自动删除已证明由本任务创建、确认可丢弃且删除行为位于授权边界内的产物；对预存、用户所有或来源不明的产物只做报告。

对重大工作，在有全新审核者或子代理可用时进行最小上下文泄漏的独立审核；不可用时用独立问题集执行一次干净复审并明确披露没有独立审核者，若剩余风险无法降到足以完成的水平则升级处理。通过检查证据解决审核者分歧，不得把多数意见当作完成门槛。修复重大审核发现后，重新运行其证伪路径以及该修复可能影响的所有集成门槛。

**完成门控：**
- [ ] 每个完成门槛有当前直接证据
- [ ] 变更差异与周边契约已审查（职责泄漏/概念重复/失效分支/用户改动重叠）
- [ ] 真实运行面已验证（含失败、恢复、销毁、边界状态）
- [ ] 工作树与文件清单已对照基线核对

**推进/回退：** 满足→进入决定；发现缺口→回阶段 3 或 5。

### 7. 决定迭代、完成或升级处理

| 决定 | 条件 |
|---|---|
| **迭代** | 审核产生可复现缺口、假设被证伪、重大风险未经测试，或出现更清晰职责边界 |
| **完成** | 见下方完成条件清单（全部满足） |
| **升级处理** | 继续推进需要新授权、不可用的外部状态变化，或不同选项会实质性改变结果而必须由用户选择 |

选择**迭代**时，更新控制状态，启动能够关闭该问题的最小下一切片。

选择**完成**需同时满足：
- 每个完成门槛都有当前证据；
- 集成行为在真实相关运行面正常工作；
- 没有已知且范围内的重大正确性、安全性、生命周期或可维护性问题未解决；
- 所有影响需求、不变量、完成门槛或重大风险的范围内可操作审核发现均已修复（不影响上述任何一项的非重大发现可说明理由后延后）；
- 必要文档已同步；
- 所有变更和临时产物均已核对。

避免无休止打磨：当方案已被证据明确证明占优，后续审核只产生低价值、范围外发现时停止扩展备选。只有当改进不影响任何完成门槛、不消除任何重大风险、也不解锁请求结果时才延后它。若用户给出"继续推进"或"不要停止"等终止性指令，只要仍有安全且范围内的工作，就继续循环。

## 有目的地编排子代理

使用子代理增加独立证据和吞吐量，而不是外包所有权。主代理负责控制状态、集成、最终验证和完成决策。

| 何时派发子代理 | 何时自己做 |
|---|---|
| 独立、有界的问题（代码考古、外部研究、备选设计、隔离实现、运行期探索、对抗审核） | 跨模块集成、控制状态维护、完成决策 |
| 不确定性高、需并行取证 | 边界明确、直接证据已充分 |
| 文件所有权可独占、不重叠 | 需要全局一致性判断 |

派发要求：为每个代理提供目标、原始材料、所属范围、允许操作、必需证据和停止条件（见 [references/control-state.md](references/control-state.md) 的子代理简报模板）。要求实现代理声明可能写入所属源码之外的命令和路径；除非隔离环境保证不重叠，否则仓库级变更命令仅由集成负责人串行执行。要求代理立即报告所属范围外的任何文件系统变化。对审核和前向测试，不得泄漏预期答案、疑似缺陷或既有结论，只传递原始产物和真实任务。把代理报告视为待验证主张，集成前检查其引用的代码、变更、测试、日志或来源；以事实来源解决矛盾，缺少证据时发送聚焦追问并及时停止已过时的工作。无论由谁执行，外部状态变更和破坏性操作都必须位于原始用户授权内。

## 只沟通重大进展

- 先说明预期结果和当前阶段。
- 报告会改变模型、范围、计划、风险或用户可见结果的发现；假设变得重要时明确说明。
- 不叙述每条命令、没有变化的等待或例行测试。
- 最终回复必须自包含：先给出达成结果，再总结重大设计发现，引用变更产物，报告验证证据，并披露剩余风险或延后工作。

## 拒绝虚假进展

以下任何一项都不能视为完成：

- 在读取事实来源前写出的详细计划；
- 只满足示例而未满足底层结果的实现；
- 只有单元测试通过、缺少相关集成或运行期证据；
- 面向用户的流程从未实际操作，仅构建成功；
- 多个代理达成一致但没有独立证据；
- 与完成门槛无关的大范围清理；
- 没有产生新证据的重复审核；
- 审核已发现重大缺口，却在第一个可工作版本处停止。
